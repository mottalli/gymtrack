# Gymtrack frontend

React + TypeScript + Vite, based on the selected **one set at a time** interaction
model and blue-and-white visual direction. The app uses the Kotlin GraphQL
backend and SQLite; see the [root README](../README.md) for the unified build.
Earlier design studies remain independent in [`prototypes/`](./prototypes).

## Local development

The recommended command is `./gradlew run` from the repository root. It serves
the compiled frontend, assets and GraphQL through Ktor on **port 8080**.
It watches/rebuilds frontend files and refreshes the browser automatically;
Kotlin/resource changes recompile/restart Ktor. It downloads the required Node
tooling, so no system npm is needed. No frontend HTTP port needs to be exposed.

For standalone frontend commands, Node 22.12+ is recommended. On this server:

```sh
export PATH="/home/marcelo/.local/share/pi-node/current/bin:$PATH"
cd /home/marcelo/src/gihub.com/mottalli/gymtrack/frontend
npm ci
npm run dev
```

The app runs at <http://localhost:5173>. Stop the old prototype server first
if it is still using that port. The strict port setting reports a conflict
rather than silently moving to another port. Run `./gradlew runStatic` from the root
in another terminal: Vite proxies `/graphql` to Ktor on port 8080.
This standalone Vite workflow is optional; `./gradlew run` does not need it.

In a separate terminal, start the component workshop:

```sh
npm run storybook
```

Storybook runs at <http://localhost:6006>, without opening a browser on the server.
Both servers bind to loopback. From your own computer:

```sh
ssh -N -L 5173:127.0.0.1:5173 -L 6006:127.0.0.1:6006 your-server
```

Open the same localhost URLs in your browser.

## Storybook

Initialized using `npm create storybook@latest` (Storybook 10.6.6), followed by
`npx storybook skills setup` and its setup instructions.

- Shared app styles and preview decoration in `.storybook/preview.tsx`.
- Colocated stories for `NumberStepper`, `SetLogger`, `SetList`, and `WorkoutPage`.
- Blank, weighted, fractional, warm-up, reps-only, editing, and workout states.
- Interaction tests plus a computed-style `CssCheck` to verify app CSS is loaded.
- Accessibility checks, autogenerated docs, and Vitest/Playwright integration.
- MSW is configured and its worker is in `public/`. Component stories use
  supplied props rather than the network, so no handlers are needed yet.
  The real app loads plans/history and saves sets through `src/api.ts`.
- Generated Storybook demo components/stories were removed after the real
  component stories passed.

## Checks

```sh
npm run typecheck
npm run lint
npm test                 # All Storybook tests in headless Chromium
npm run test:e2e         # Full workout flow, history persistence, mobile widths
npm run build
npm run build-storybook
```

For a new machine, install the browser first:

```sh
npx playwright install chromium
```

If OS libraries are missing, `npx playwright install chromium --with-deps`
may require administrator privileges. E2E tests start their own loopback
Ktor server with a temporary SQLite database on port 18180 and save screenshots
to `screenshots/` (gitignored). They build a runnable distribution through Gradle.

```text
  api.ts                  GraphQL client and DTO-to-UI mapping (grams ↔ kg)
  domain.ts               Typed frontend models and sample plan fixtures
  components/
    NumberStepper.tsx     + [number] −, also supports direct entry
    SetLogger.tsx         One-set entry, warm-up toggle, editing
    SetList.tsx           Warm-ups first, tap to edit previous sets

```

## Behavior and limitations

- The database supplies the exercise lists and rep ranges provided by the user,
  with four exercises per day and three working sets per exercise, excluding warm-ups.
- Storybook uses independent sample fixtures for isolated UI scenarios.
- New sets carry over the last logged set's values. The first working set uses
  the upper rep target and suggested weight (blank weight if unavailable).
  The first warm-up starts blank. Prefilling never records a set automatically.
- Tap controls increment by 1 rep / 1 kg. Direct weight entry accepts fractions.
- Users may log any number of working or warm-up sets.
- The first two logged sets per exercise default to warm-ups, with warm-up
  colouring applied immediately. Users can override this; editing preserves
  the recorded set type. Later sets default to working sets.
- A weight suggestion repeats the last recorded working weight for that exercise.
  No progression maths is implemented, and no suggestion appears without history.
- Sets are saved to SQLite immediately when logged or edited. All started
  sessions appear in history; there is no persisted completion state.
- Recorded sets survive reloads and can be resumed from history. Unsubmitted
  set-entry drafts reset on exercise navigation. Failed saves retain their inputs.
- Previous localStorage-only history is not automatically imported.
- Next-workout suggestions follow the latest session's position in
  the plan; users can always choose any workout.
- Statistics and plan editing remain out of scope.

Vite is pinned to major 7: the latest Vite scaffold used major 8, whose native
tooling crashed with `Illegal instruction` on this headless server. Vite 7,
the app build, and Storybook work here without that tooling.

`npm audit` currently reports 14 moderate findings in transitive development
tooling (glob/minimatch via Storybook and ESLint). Compatible automatic fixes
were attempted; npm's remaining suggested fixes downgrade major tools.
No `--force` changes were applied.
